# Onboard the company: the Board interview

You are the CEO. In about 45 minutes, replace the `TODO(board)` facts in `knowledge/company/` and `knowledge/products/` with the Board's own answers, set `company.json`, read out what is on by default and record what the Board wants stricter, and collect what engineering needs to deploy safely (SA-001). **Write each round's answers into the KB before you ask the next round.**

## 1. Prepare (no questions yet)

1. File this as a directive, following the `directive` skill's filing step: `D-<YYYYMMDD>-onboard-company`. Use the Board's words that started it, or "/onboard-company".
2. Read `knowledge/INDEX.md`, every page in `knowledge/company/`, `knowledge/board/charter.md`, `knowledge/board/standing-authorizations.md`, every `knowledge/products/*/README.md`, `company.json` if it exists, `docs/optional-integrations.md` and `docs/guards.md`.
3. Read `knowledge/engineering/architecture/*.md` and `knowledge/engineering/runbooks/*.md` if they exist. **Facts the code already shows become confirm-style questions**, e.g. "The repo deploys to Vercel from `main` via GitHub Actions. Is that how production works today?". That's faster for the Board than open questions.
4. List the open facts: `grep -rn "TODO(board)" knowledge/ --include="*.md"`.
5. Tell the Board the agenda in a few lines: the rounds below, about 45 minutes, and that it can say "skip", "later" or "stop" at any time. Say that the defaults of round 8 are already in force, and that the Board may hear them first. Mention that the interview itself sends nothing outside the company, and that secrets mustn't be pasted, only where they live.

## 2. Interview rounds

Ask **3–5 numbered questions per message**, as plain text in the chat, then wait for the answers (the Board started this interview; never AskUserQuestion to the Board). Skip anything the KB already answers. Give a recommendation or a guess-to-confirm only where the code or KB supports it, and label it as such.

## 3. Rules while recording

- **Quote the Board** where wording matters: mission, vision, claims about the product, every stricter choice and authorization. Paraphrase only plain facts. A kept default is recorded nowhere as the Board's words.
- **Unanswered stays `TODO(board)`,** for a fact; for a default, unanswered keeps the default. Sharpen the question so next time it's quick to answer. Never fill a gap with a guess, and never read silence as a grant of anything that isn't on by default.
- **If the Board pastes a secret,** don't write it anywhere. Record only where it lives, and tell the Board you didn't store the value.
- **A standing authorization is narrowed or ended, and a template or a new one granted, only in the Board's own words,** quoted with the date in an `Amended`, `Ended` or `Granted` line in `knowledge/board/standing-authorizations.md`; `charter.md` the same. A new one is the next `SA-NNN` section.
- **A stricter choice holds from that answer.** Record it at once; send the platform engineer the order where the list names it; a line in `.claude/settings.json` goes out only by the main session, on the Board's own message.
- **`company.json`** (a guardrail file: the guards read it). Only you, in the main session, write it, after showing the Board the exact text and getting its yes; the hook asks the Board again at the write, and that prompt is the Board's to answer. Create it at the repo root if it's missing. Its keys: `company_name`; `board_email` (the only address you may email; empty: you email nobody; with an address, the same shown text also has, as the default, `"board_email_events": {"from": "<the current UTC time, as date -u +%Y-%m-%dT%H:%M:%SZ prints it>"}` under `integrations`: from then on the capacity scan reminds you of an event's email that didn't go out; leave it out to switch it off); `timezone` (IANA name); `products` (`{"<id>": {"repo": "<owner>/<name>", "workspace": "workspaces/<id>/<name>"}}`); `integrations` (`{"<name>": {<its settings>}}`, the names and settings in each integration's own page; one that isn't there isn't set up, so no `board_desk` entry, nor any other, until the Board's yes to it; a setting left out takes its page's default). Afterwards check it: `python3 -c "import sys; sys.path.insert(0, 'scripts'); import company_config as c; print(c.load()); print(c.timezone())"`. A broken file makes the guards refuse, so fix it at once. Then commit it alone (`kb(D-<id>): company.json`), with a status-log row `ASK 1 b9: taken` quoting the Board's yes: the system check counts only such a commit as landed.
- Update `updated:` on every page you change. Set a page's status to `active` once its main sections are filled. Leave it `draft` while most of it is still `TODO(board)`.

## 4. After the interview

1. **For each product whose deploy facts are now known,** send the CTO an ORDER (size S, logged in this directive). If its architecture page is missing, the order is `/onboard-codebase <product>` first. It asks the CTO to update `knowledge/engineering/runbooks/<product>.md` with the confirmed facts, verify every non-destructive step it can (build, test, smoke check against production), and report which steps remain unverified. The runbook becomes `active` only when the CTO reports the steps verified.
2. **For each department or integration switched on,** follow its page's set-up with the Board, one step at a time; a step that needs a change to the system goes through the platform engineer and the gate.
3. Run the first system check (`/system-check`): its row is the baseline the next one compares with.
4. Update `knowledge/company/how-it-works.md` ("Live, off, being built", "Last checked"). Run `python3 scripts/kb_lint.py` and fix any errors in your pages.
5. Commit the rest (`kb(D-<id>): record onboarding answers`) and push to the company's own private remote.
6. Report to the Board: what's filled, what's still `TODO(board)` (grouped), each default the Board made stricter (and that the rest stand), the orders sent, and **a proposed first S-size directive** for one product, with your reason for choosing it.
