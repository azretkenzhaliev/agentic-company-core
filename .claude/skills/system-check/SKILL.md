# The system check (`ceo.md`, "System changes")

You are the CEO. This is step 1 of the gate in `ceo.md`, "System changes", word for word: run it before you send the platform engineer an order that names a guardrail file (`platform-engineer.md`, "The gate") or when you can't tell, and after every report (step 3), which never drops: it compares with the last committed `System check` row, so any change not landed since then and still there is caught. It is the gate's own text: it changes only through the platform engineer and the gate (`platform-engineer.md`, "The gate").

1. **Before the order,** in the main checkout, run `mkdir -p workspaces/system/user-settings`, `git status --porcelain -- .claude scripts CLAUDE.md company.json tools knowledge/_templates .gitignore`, `git log --oneline <HEAD at the last check>..HEAD --` on the same paths, `diff workspaces/system/settings.local.last.json .claude/settings.local.json` (gitignored, so git can't see it), `diff workspaces/system/user-settings/claude.settings.json ~/.claude/settings.json` (a gitignored copy: a hash alone can't bring back an overwritten file), `shasum -a 256 .claude/settings.local.json workspaces/system/settings.local.last.json ~/.claude/settings.json workspaces/system/user-settings/claude.settings.json .git/config .git/info/exclude` (on Linux, `sha256sum`) and `ls .git/hooks/` (sample files aside). If the Board runs Claude Code with a second configuration folder (`CLAUDE_CONFIG_DIR`), its `settings.json` gets the same `diff` and hash, with its own copy beside the first (`<folder name>.settings.json`). A file that doesn't exist is logged as `none`. Compare them with the last `System check` row in committed history (`git grep -hE "^[|] [0-9-]{10} [|] ceo [|] System check [0-9]{4}-" HEAD -- knowledge/board/directives/`, which prints the rows only; the latest by its UTC time, not by where it comes in the output; a row timed after this check is reported, not used) and act on what differs (below). Then log this check's row in the directive's status log, as things stand after it, in this shape (each file above with its hash; the hooks but the samples): `| <date> | ceo | System check <YYYY-MM-DDTHH:MM[:SS]Z>: HEAD <sha>; sha256 <file> <hash>; ...; .git/hooks: <list or none> |` (e.g. `System check 2026-01-01T09:30:15Z:`; the grep above misses a row without the date, and `scripts/kb_lint.py` flags one), never a file's entries (one may hold a token). Commit it alone: your other edits to that file go in their own commit first, and a line you didn't write is reported, not committed; while the file still holds one, stage the row alone (`git diff -U0 -- <file>`, its header and the row's hunk saved as a patch in your scratchpad, not the repo, then `git apply --cached --unidiff-zero <patch>`, and the patch deleted after). `git diff --cached` shows only the row's lines. With no row yet, this check's row is the baseline, and its `git log` runs from the last landing the status log names (`Landed <sha>`), or else from the commit your copy started from. A field no committed row has yet takes this check's value as its baseline; a field the last row lacks is compared with the latest row that has it.
   - **Anything not landed** (a change `git status` shows, or a commit in that `git log` you didn't land through this gate): save `git status`, `git diff HEAD` on those paths, each new file's text and `git show` of each such commit to `workspaces/system/reverted-<date>.txt` as evidence, report it, and revert it (`git restore --source=HEAD --staged --worktree -- <path>`, a new file deleted once saved; `git revert` for a commit), unless the Board has said it made it itself (its own maintenance session, or a core update it merged by hand). A commit that only wrote `company.json` from your own main session, after the Board's yes to the exact text, quoted in a status-log row, counts as landed.
   - **`settings.local.json` differs from the last copy** (any line added, deleted or changed): save the `diff` in `reverted-<date>.txt` (gitignored, so a token stays out of git), report it, and restore the last copy whole, unless the Board says it made the change (then the file becomes the new copy). A copy whose hash isn't the last row's hash of the file was rewritten: report that at once. **First run,** with no copy yet: show the Board the file's entries in one line each, and once it says they are its own, copy the file to `workspaces/system/settings.local.last.json`.
   - **A changed hash of a user file** (`~/…`), or a `diff` against its copy: save the `diff` in `reverted-<date>.txt` and tell the Board at once which file changed. Those files are the Board's: you don't restore them. Keep the old copy until the Board says the change is its own (then the file becomes the new copy); if the Board says it isn't, the copy is what it restores from. A copy whose hash isn't its hash in the last row was rewritten: report that at once. **With no copy yet:** `mkdir -p workspaces/system/user-settings`, `cp -n ~/.claude/settings.json workspaces/system/user-settings/claude.settings.json` (`-n`: never over a copy that exists).
   - **A changed hash of `.git/config` or `.git/info/exclude`, or a changed `.git/hooks/` list:** the same: tell the Board at once, and don't restore it. Every worktree shares them and they act on the main checkout's own git commands (`.git/info/exclude` can hide files from `git status`, like `.gitignore`); the Board's own tools also write `.git/config` (an editor, `gh`).
