# Testing standards

1. **Every behavior change has a test** that fails without the change and passes with it. Write the test first where practical, and watch it fail.
2. **Bug fixes start with a test that reproduces the bug.**
3. **Run the suite your step needs,** with the commands in the product's runbook, not only your new tests. Report the exact commands and results. A failure you didn't cause still goes in your report, by name.
   - **While a task iterates** (Senior, code reviewer): the **task suite**, the suites the task's diff can affect (the runbook's "Task suite", where the product has one).
   - **At a landing:** after merging `origin/main`, the task suite and the runbook's **essential tier** (where it has one) on the founder's machine, then the required checks (engineering README §5). Zero tests selected for a code change fails the gate.
   - **For a production deploy:** the affected tests, the essential tier and the PR's CI checks (engineering README §5; SA-001 condition 2: no full suite before a deploy or on a schedule). Where a push to `main` is the deploy, that is each landing's affected and essential run. Nobody repeats a run on the same tree (README §4, "One tree, one full run").
4. **Test real behavior.** Mock only what you can't run (paid services, production systems, the network). Never assert on mock calls when you can assert on results.
5. **No network or production data in tests.** No real credentials.
6. **Deterministic.** No sleeps for timing, no dependence on test order, the clock or randomness without seeding. A check that output lacks a short key (`not.toContain("f01")`) matches it as a whole word, or the output's ids are fixed: a random hex id can hold the key.
7. **Cover the edges** the acceptance criteria imply: empty, too long, invalid, unauthorized, duplicate, concurrent where relevant.
8. **A repo without tests:** add the smallest test setup that fits its stack, in the design doc (M and L) or as its own S-size task. Don't silently skip testing.
9. **Tests hold up when other workstreams land:**
   - A test that builds its own registry, fixture bank or config overrides every part it depends on together (for example both `types` and `templates`), and never assumes another workstream's content is absent from the shared defaults.
   - Tests that do slow work (whole runs, enumerations, child processes) set an explicit timeout instead of relying on the runner's default, so they pass on a machine shared by parallel workstreams.
10. **Platform checks and spikes must be able to fail.** When a test records how a platform behaves (a browser, an operating system, a cloud API) rather than our code:
    - a `pass` rests on the mechanism's own evidence (its error code, its message, its event naming the file), never on something merely not happening (a missing marker, a file not appearing);
    - each such check has a control run in which the mechanism is off and the thing does happen, through the same path;
    - the fixture can't produce the outcome by itself (e.g. a server that never finishes a body makes every download look held);
    - a reading is derived from what was observed, never written because a step ran;
    - outcomes that are results, not requirements, are recorded (and stated in the report), so a platform change shows up instead of failing silently or passing vacuously.
11. **A check that must agree with another parser is tested against that parser.** When our code validates a string that a library then parses (a database URL, a MIME header, a path, HTML), a test runs the library's own parser on the same inputs and asserts it reads what our check approved: generated shapes, not one example, covering every code point at each boundary, escapes and repeats. One probe that "reads the same" isn't evidence: a parser can have a second path that a plain input never takes.
12. **Mutation checks run only when the design or task spec asks, and then in a copy, never in the worktree.** To show a test fails without the code or data it guards, export the commit into your own scratchpad (`git archive <commit> | tar -x -C <scratchpad>/copy`), mutate and run there, and say which line failed. Never edit a tracked file in the shared worktree "temporarily": a stop mid-check leaves the change behind, and the permission system may refuse it as a change to a shared resource. Specs that ask for a mutation say "in a scratch copy".
13. **A module mock keeps the real module's other exports.** A process-wide mock (Bun's `mock.module`, for one) outlives the file that sets it, so a partial mock changes what every later file imports, and a test can pass or fail with the run order. Mock as `{ ...(await import("<module>")), <the overrides> }` and say in a comment that it outlives the file. A task that adds a test mocking a shared module also shows the new file passing after and before each other file that mocks the same module (two-file runs, both orders).
14. **Timing tests survive a shared CI runner.** A test that asserts a time bound sets it at least 3 times above the slowest local run of the same input, or asserts growth (the time at 2N against N) instead of an absolute bound. A timing test that fails once on CI and passes on a re-run is a flake to fix, not to re-run forever. **In-process work is timed in CPU time, not wall time.** Wall time is used only for a wait on another process (a child's start), scaled by one named factor. A changed bound shows once, by a temporary edit in a scratch copy, that 10x or quadratic work still fails it.
15. **Under machine load, and the tests a task changes.** (a) A test that fails is a failure, on a loaded machine too. The runbook sets a per-test bound a busy machine doesn't reach and a real hang does; a slow test is fixed at its cause. A re-run alone once (that file only, both runs reported) is allowed only for a flake the runbook names, each with its fix planned. The product's runbook limits how many heavy runs go at once. (b) A task's ORDER names the existing tests the task may change, including those that pin a list, count or registry it adds to (`grep` the registry's name in the test folders before writing the spec); a Senior who must change another one says which and why in its report, never "the file's other tests".
16. **A rule keyed on the parsed shape is tested from the raw input once.** When a rule or exception depends on how the parser represents something (a link's kind and text, nested parts, headers), at least one test starts from a raw input and runs the engine on the parsed result. Hand-built parsed fixtures stay fine for everything else, but the review checks that each hand-built shape is one the parser can produce.
17. **Code that reads hostile input stays linear, and every fix proves it.** For parsers of uploaded files, HTML, URLs and the like: (a) no regex with an alternation or a quantified group inside a repetition, or two adjacent quantifiers that can match the same text, on attacker-controlled input; skip comments, whitespace and prologs with a linear `indexOf` loop; (b) every loop or regex a task or a fix adds or changes on such input gets a scaling test at n, 2n and 4n **under the production runtime** (rule 14's growth form); a regex counts as a loop; (c) a fix ORDER for a review of such code asks for the scaling tests and for the earlier rounds' probes and benign samples re-run with a before/after table. (d) **The shape scales every dimension,** not one list: shared references, nested lists and string length too. (e) **Linear isn't enough:** the worst shape the real producer can emit, at its real caps and in production's modes, also holds an absolute budget.
18. **Each test file stands on its own.** CI may run the files in shards, so any file may run first, or after any other. A file builds or seeds what it needs in its own `beforeAll`, and leaves shared rows (global tables, seeded settings) as it found them, in an `afterAll`; the reviewer checks it. A test that fails in a shard and passes alone is a dependence on file order, not a flake: fix it in the test. A local run isn't a fresh checkout (gitignored build outputs stay), so for a change to how tests are split or set up, the PR's CI is the proof.
19. **A selection's size is measured and reported,** where a product selects tests. "Affected" means the tests the diff reaches, plus a small named set (the essential tier, a whole-tree tier), and nothing else.
    - Every selection prints and writes to the job summary "selected N of M tests (reached R; tiers: ...)". A CI change that touches selection reports N of M for three sample changes (a page, a server module, a shared package) before and after, with run ids.
    - A test pins, on the real tree, that a one-file change selects a small share of it, with the threshold and its reason in a comment.
    - **A tier that runs on every change (an "always" set) needs the CEO's yes:** a suite already green on the same code doesn't run again. A rule that picks tests by what they read, not by what the diff reaches, is such a tier.
    - Tests run once per change, on the code that lands: where there is a merge queue, in the queue on the merge result, not again on the pull request or on the push that follows.
    - **A change to reuse or skip logic is dry-run on real history before it lands.** For each trigger it changes, run the new rule on the last three real runs. Report the command and what it answers, and whether a record was found.
20. **A test of a tunable reads the tunable from the settings' defaults** ([runtime-settings.md](runtime-settings.md)). A test that checks a value we may tweak (a tick's time budget, a chunk size, a lane count, a threshold) reads it from the settings' defaults through the product's settings reader, and derives what it expects from that value. Never a literal of the value in the test's code or in its name. A reviewer treats such a literal as a major finding. Until the reader is on `main`, the test imports the value from the one module that defines it, never a copy. A test that checks behaviour at a fixed size of its own choosing passes that value in explicitly as its input, named by its role (`SHORT_TICK`, not `BOUND_45S`), so the default can change under it without breaking it.
21. **A check's failure output carries what it saw.** A staging or end-to-end check that stops early prints the facts it gathered up to the stop, or says "not counted", never a zero it did not measure. A test proves it. A limit the check sizes its load against is pinned by a test to the path the check actually drives.
22. **A timing bound holds on the slowest runner that runs the test.**
    - An emulated runner can start a child process ten times slower than a native one.
    - A test never hands a real child or process start a budget that only native speed meets. Give it the ordinary limit, and keep the test's own clock in the test.
    - Before a change of runner, its owner runs the affected files once in the slower form.
23. **No RegExp built from a variable, in tests too,** where the repo's security scan blocks it (semgrep's `detect-non-literal-regexp`, for one) and the scan isn't installed on the machine the review runs on: a reviewed head would fail it only after the push. Compare exact text instead (`toBe`, `endsWith`, `includes`) or write the pattern as a literal; a reviewer flags any `new RegExp(` with a non-literal argument in the diff.
